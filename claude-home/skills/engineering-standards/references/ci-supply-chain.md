# CI and supply chain

For GitHub Actions changes, follow the repository workflow contract and current
[official documentation](https://docs.github.com/en/actions). Use
[diagnose](../../diagnose/SKILL.md) for an observed orchestration failure. The
following are cross-platform supply-chain invariants.

- Keep lockfiles committed and install dependencies from the lockfile in CI. Review dependency and lockfile diffs deliberately.
- Pin third-party CI actions and container bases to immutable digests or full commits (or lock them in the platform's workflow dependency lockfile), with an update mechanism; a mutable tag is not a sufficient security boundary.
- Prefer short-lived federated identity to static CI credentials. Limit token permissions, avoid unsafe fork-triggered workflows, and prevent untrusted PR data from reaching shell, privileged contexts, or deployment credentials.
- Treat provenance as build identity, not proof that an upstream package or pipeline is safe. Scan the shipped artifact when the project supports it.
- Preserve local/CI parity where feasible; do not introduce a mandatory CI gate that cannot be reproduced or explained from the repository.

GitHub Actions specifics ([secure use](https://docs.github.com/en/actions/reference/security/secure-use), read 2026-10-24):

- Top-level `permissions` is `contents: read` or `{}`, raised per job. `actions/checkout` sets `persist-credentials: false` unless a later step pushes. A SHA pin carries a version comment. A repository that adopts the workflow dependency lockfile (GA 2026-10-28, [changelog](https://github.blog/changelog/2026-10-28-github-actions-workflow-lockfiles-are-generally-available/), read 2026-11-11) keeps readable tag refs in `uses:` and commits `.github/workflows/actions.lock`, generated by `gh actions-lock` and checked in CI with `gh actions-lock --verify`; never hand-edit it. A lockfile fixes which commit runs, not whether it is safe.
- Event, input and ref values reach `run:` through `env:`, never inline `${{ }}`. Never check out or run pull-request code in a [`pull_request_target`](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target) or `workflow_run` job that holds secrets or a write token. From 2026-12-02 public repositories block `pull_request_target` by default unless an Actions event policy allows it ([changelog](https://github.blog/changelog/2026-11-02-pull_request_target-blocked-by-default-december-2/), read 2026-11-11): prefer `pull_request`, and report a workflow that still needs the trigger as needing that policy.
- Every job has `timeout-minutes`; `concurrency` cancels superseded PR runs, never release or deploy runs. Cache keys hash the lockfile, and untrusted jobs never write caches that release jobs restore.
- Keep required-check names, triggers and thresholds, and report any change as a merge-protection impact; a path filter must not leave a required check pending, so add an aggregator job that always runs.
- Validate with `actionlint`, `zizmor` and `shellcheck` on `run:` scripts. A speed claim needs durations of comparable runs before and after.
