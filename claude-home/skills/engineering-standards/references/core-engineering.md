# Core engineering

- Start from observed behavior: inspect the relevant source, tests, logs, configuration, or data before forming a hypothesis. Test one hypothesis at a time, fix the root cause minimally, and verify the result.
- Prefer less code: reuse an in-repo pattern, the standard library, a platform primitive, or an existing dependency before adding a new dependency. Extract only after a second real repetition; do not create speculative abstractions.
- Keep the global 800 physical lines per code file and 7 direct code files per directory, including tests and scripts. Divide affected modules by responsibility, preserving interfaces and updating consumers; do not compress code or relabel owned code as generated to pass.
- Run `python3 ~/.pi/agent/claude-home/bin/structure/structure.py --project-root ROOT --json` and any stricter repository gate before claiming structural compliance. Report existing violations; split affected modules without unrelated mass rewrites. A text instruction alone is not enforcement.
- Apply single responsibility at function, file and directory levels: name the coherent behavior or domain each owns. Split oversized directories into meaningful subdomains with explicit interfaces, never numbered buckets or hidden files.
- Centralize shared rules within their owning domain. Use Generic<T> or language equivalents for actual reusable behavior with preserved type relationships across inputs, members or outputs (including inferred returns), constraints and inference; avoid unnecessary type parameters, unchecked casts and cross-domain coupling.
- Prefer current stable, maintained architecture with explicit dependency direction. For a migration, establish compatibility, concrete benefit, acceptance checks and rollback using the task's research; newness alone is not a benefit.
- Use intent-revealing names and local conventions. Keep functions focused, use guard clauses where they clarify flow, and make errors visible with useful context. Do not swallow errors, return fake success, leave delivered placeholders, or use exceptions for ordinary control flow.
- Keep ownership and boundaries explicit. Do not create catch-all `utils`, `helpers`, `common`, or `shared` directories to avoid a real architecture decision.
- Keep ordinary bounded changes direct. Seek an independent review for substantial risk, such as security, persistent data, concurrency, irreversible impact, incompatible public contracts or consequential architecture, when delegation is authorized and fresh context can resolve a concrete question. Routine branching logic alone does not require a reviewer. Provide the artifact and contract, reconcile findings against evidence and avoid equivalent review lanes; a reviewer is input, not a verdict.
- Bounded recovery: for the same unresolved failure, use one attempt, one informed retry and one materially different approach, then report the concrete blocker on that path. Normal TDD cycles and distinct validated changes do not consume a blanket per-file edit limit.
